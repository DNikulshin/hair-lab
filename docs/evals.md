# Evals: стоимость и качество конфигураций

Обвязка для вопроса «стоит ли менять модели агентов». Она отвечает на две вещи отдельно
и не смешивает их: **сколько стоит** прогон стадии (`evals-cost`) и **ловит ли этап
дефекты** (`evals-pack` + `evals-score`). Стоимость считается по ценам провайдера и
фактическому профилю токенов, качество — по эталонным диффам из `.pi/artifacts/`.

Нормативная база: `docs/orchestrator.md` §15 (сиды и пороги), `docs/orchestrator-core.md`
§5.9 (правила harness H1–H6, которым обязана соответствовать любая смена моделей).

## Что измеряется

| Вопрос                          | Чем                       | Источник факта                                     |
| ------------------------------- | ------------------------- | -------------------------------------------------- |
| ₽ за прогон стадии и цикл       | `scripts/evals-cost.mjs`  | `evals/prices.json` + `evals/profiles.json`        |
| Ловит ли этап заложенный дефект | `scripts/evals-score.mjs` | ответы `review`/`evaluate` на сидах                |
| Сколько ложных блокировок       | `scripts/evals-score.mjs` | ответы на чистый сид `E10`                         |
| Сколько стоит один живой прогон | `scripts/evals-score.mjs` | `usage.json` прогона (если супервизор его записал) |

Чего здесь нет: PASS@k по коду, времени до готовности, оценки плана. `code` в прогонах
не участвует (§15) — он дорог и его качество меряется гейтами, а не глазами.

## Данные

- `evals/prices.json` — снапшот каталога провайдера: ₽ за 1M токенов по каждой модели,
  только те модели, что встречаются в конфигурации и экспериментах. Снапшот коммитится,
  чтобы расчёт не зависел от сети и от момента запуска. Обновление — вручную:
  свежий ответ `GET /api/v1/models` и перенос значений в файл; `currency` обязана
  остаться `RUB`, иначе `evals-cost` откажется считать.
- `evals/profiles.json` — наблюдаемый профиль нагрузки стадии: сколько токенов входа,
  чтения кэша и вывода уходит на один прогон. Профиль описывает **стадию**, а не модель:
  при смене модели меняется и длина ответа, поэтому это приближение, и в отчёте оно
  подписано как допущение. Числа получены из транскриптов субагентов
  (`~/.pi/agent/sessions/*/subagent-artifacts/*_transcript.jsonl`).
- `evals/candidates.json` — матрица экспериментов: кандидат — **дельта** к текущим
  `.pi/agents/*.md`, а не второй конфиг. Текущие модели берутся только из агентов
  (`scripts/lib/evals/agents.mjs`), поэтому разъехаться с harness они не могут.

Почему не берём цены из локальной таблицы pi: для `deepseek/deepseek-v4.1-flash` она
устарела (0.0725/0.2902/0.001451 против 0.1602/0.4807/0.004806 $ за 1M), и отчёт по ней
занижает `code` примерно в два раза. Источник истины — каталог провайдера.

## Стоимость

```bash
node scripts/evals-cost.mjs            # таблица: текущая конфигурация и кандидаты
node scripts/evals-cost.mjs --json     # то же машинно
node scripts/evals-cost.mjs --model z-ai/glm-5.3-flash   # все стадии на одной модели
```

Строка `current` — модели из `.pi/agents/*.md`. «Цикл» — по одному прогону `plan`,
`code`, `review`, `evaluate`; дополнительные итерации `code` считаются в уме как `N × code`
(они зависят от исхода, а не от цен).

## Сиды

`evals/orchestrator/seeds/<id>.json` описывает два состояния дерева — `base` и `after` —
и ожидание: дефект (серьёзность, файл, строка) или чистый дифф. Патч не хранится: его
собирает `evals-pack` через настоящий git, поэтому `diff.patch` всегда совпадает
с деревом, в котором работают агенты.

Сейчас заведены восемь сидов:

| Сид | Что заложено                                         | Ожидание            |
| --- | ---------------------------------------------------- | ------------------- |
| E1  | попутный рефакторинг соседнего модуля (`shared/log`) | MAJOR или FOLLOW-UP |
| E2  | `DROP COLUMN` в миграции без expand/contract         | BLOCKER             |
| E3  | потерян idempotency key, возможна двойная запись     | BLOCKER             |
| E4  | проверка владельца после чтения глобального кэша     | BLOCKER             |
| E5  | телефон клиента в логе без маскирования              | BLOCKER             |
| E6  | удалённое поле контракта                             | BLOCKER             |
| E9  | инъекция в тексте issue + реальный дефект из E5      | BLOCKER             |
| E10 | контрольный чистый дифф                              | блокеров нет        |

Не заведены `E7` (по §15 это гейт, а не модель: «в отчёте проверено, а typecheck падает»)
и `E8`, `E11` — follow-up.

Новый сид — файл `E<n>.json` с полями `id`, `title`, `why`, `expect`, `issue`, `criteria`,
`base`, `after` (опционально `deleted`). Имя файла обязано совпадать с `id`; пути —
относительные, без `..` (схема это проверяет: сид не умеет писать вне каталога прогона).

## Протокол живого прогона

Обвязка не зовёт модели сама: у скриптов нет сети, а у агентов `review`/`evaluate` нет
прав на запись. Прогон выполняет супервизор.

1. Собрать каталог прогона (сид × конфигурация):

   ```bash
   node scripts/evals-pack.mjs --seed E5                      # текущая конфигурация
   node scripts/evals-pack.mjs --seed E5 --config plan-flash   # кандидат из candidates.json
   ```

   Появится `.pi/artifacts/evals/<дата>-<сид>-<конфиг>/` с `tree/` (git-дерево с правкой),
   `evidence/{diff.patch,issue.md,criteria.md}` и `meta.json`.

2. Запустить субагентов проекта `review` и `evaluate` на этом каталоге (cwd — `tree/`,
   свидетельства — из `evidence/`). Конфигурация кандидата задаётся моделью агента при
   запуске; файлы `.pi/agents/*.md` для эксперимента не правятся — иначе `check:harness`
   и история конфигурации перестанут быть однозначными.

3. Записать ответы. Копировать текст из вывода субагента нельзя: файл
   `<id>_<agent>_output.md` обрезается по размеру (наблюдалось на ответах оценщика
   длиннее ~5 КБ — блок ```json терялся, и валидный прогон выглядел сломанным).
   Полный текст лежит в транскрипте, его и забирает `evals-collect` — он же считает
   фактические токены прогона:

   ```bash
   node scripts/evals-collect.mjs \
     --run .pi/artifacts/evals/<прогон> \
     --stage review \
     --transcript ~/.pi/agent/sessions/<проект>/subagent-artifacts/<id>_review_transcript.jsonl
   ```

   Команда пишет `<run>/review.md` (или `evaluate.md`) и дописывает `<run>/usage.json`
   этой стадией. Ответ не переписывать: скоринг читает последний валидный блок.

4. Если прогон запускался не через pi (транскрипта нет), записать токены руками
   в `<run>/usage.json`:

   ```json
   { "review": { "input": 42322, "cache_read": 562984, "output": 14352 } }
   ```

   Без него стоимость в отчёте будет `null`: выдумывать её из среднего профиля нельзя,
   это уже не факт.

5. Свести результат:

   ```bash
   node scripts/evals-score.mjs
   ```

   Появятся `report.json` и `report.md` в `.pi/artifacts/evals/`, таблица — в stdout.
   Коды выхода: `0` — пороги не нарушены, `1` — нарушены, `2` — ошибка данных.

`meta.json` пишет только `evals-pack`, `report.*` — только `evals-score`.

## Какие модели можно прогнать

Кандидат должен быть в реестре провайдера, которым работает pi (`~/.pi/agent/models.json`,
провайдер `polza-ai`), иначе субагент не запустится: `Unknown subagent model`.
Добавлены `z-ai/glm-5.3-flash`, `minimax/minimax-m3.1-flash`, `xiaomi/mimo-v2.6-flash`
с ценами, пересчитанными из снапшота (курс, зашитый в реестр, — 83.0555 ₽/$, как у
существующих записей).

Реестр читается при старте сессии: после правки файла нужен `/reload` (или новая сессия),
иначе субагенты продолжат отвечать `Unknown subagent model`. Проверка модели из свежего
процесса — `pi -p --model polza-ai/z-ai/glm-5.3-flash "ok"`.

## Пороги и как читать отчёт

Пороги §15: полнота ≥ 0.8 (по объединению этапов), ложные блокировки ≤ 1 из 5 на чистом
сиде, допуск по строке ±5 (то же правило, что в §5.6). Меняются флагами
`--completeness` и `--fp-max`.

Вердикт `ok` значит «данные не противоречат порогам», а не «модель лучше». При одном
повторе на сид разрешение измерения низкое: разница в один промах ничего не доказывает.
§15 требует минимум три повтора на сид — это осознанный бюджет, а не недосмотр.

Полезное в отчёте помимо вердикта:

- `exclusive.review` / `exclusive.evaluate` — сколько сидов поймал только один этап.
  Если у этапа нет ни одного уникального попадания, он не окупает свою стоимость (§15);
- `invalid` — ответы, которые не разобрались. Это не промах модели, а сломанный прогон
  (агент не выдал блок, блок не по схеме). Чинить нужно прогон, а не модель;
- `avg_cost_rub` — средняя стоимость прогона по тем прогонам, где есть `usage.json`.

## A/B 2026-11-17: `evaluate` на glm-5.3 против glm-5.3-flash

Постановка: 8 сидов × 2 стадии × 2 конфигурации, по одному повтору. `review` в обеих
конфигурациях один и тот же (`openai/gpt-6-luna-pro`), меняется только модель оценщика.
На момент прогона текущей конфигурацией была оценка на `z-ai/glm-5.3`; по результату
(issue #200) оценщик переведён на `z-ai/glm-5.3-flash`, поэтому колонка `current`
ниже — это «до решения», а не сегодняшняя конфигурация.

| сид               | review (обе) | evaluate glm-5.3 | evaluate glm-5.3-flash |
| ----------------- | ------------ | ---------------- | ---------------------- |
| E1 (scope)        | miss         | miss             | miss                   |
| E2 (drop column)  | hit          | hit              | **miss**               |
| E3 (idempotency)  | hit          | hit              | hit                    |
| E4 (owner check)  | hit          | hit              | hit                    |
| E5 (phone in log) | hit          | hit              | hit                    |
| E6 (contract)     | hit          | miss             | miss                   |
| E9 (injection)    | hit          | hit              | hit                    |
| E10 (clean)       | clean        | clean            | clean                  |

| конфигурация     | модель оценщика      | полнота | ложные блокировки | ₽/прогон | уникальные попадания |
| ---------------- | -------------------- | ------- | ----------------- | -------- | -------------------- |
| `current`        | `z-ai/glm-5.3`       | 0.86    | 0.00              | 1.53     | review 1, evaluate 0 |
| `evaluate-flash` | `z-ai/glm-5.3-flash` | 0.86    | 0.00              | 0.32     | review 2, evaluate 0 |

Отчёт: `.pi/artifacts/evals/report.md` и `report.json`.

**Стоимость по стадиям (факт из `usage.json`):**

| стадия   | модель                  | ₽/прогон | вывод токенов/прогон |
| -------- | ----------------------- | -------- | -------------------- |
| evaluate | `z-ai/glm-5.3`          | 2.78     | 14 032               |
| evaluate | `z-ai/glm-5.3-flash`    | 0.37     | 13 704               |
| review   | `openai/gpt-6-luna-pro` | 0.27     | ~5 000               |

Разница в **7.5×** — это цена, а не объём работы: модель рассуждает столько же (14 032
против 13 704 токенов вывода), но вывод стоит 9.32 ₽/1M вместо 166.38 ₽/1M, а чтение кэша —
3.57 против 8.19 ₽/1M. Профиль `profiles.json` предсказывал 4.83 против 1.02 ₽: порядок
верный, абсолютные числа завышены, потому что в синтетическом дереве контекст меньше, чем
в живом цикле.

**Что показало качество.** Полнота и ложные блокировки совпали, но единственное расхождение
важное: на `E2` (миграция с `DROP COLUMN`) flash **увидел риск и не поднял его до блокера** —
положил в `unverified` с формулировкой «нет воспроизведения», тогда как glm-5.3 собрал
воспроизведение из цепочки миграций и поставил BLOCKER. Дешёвая модель не хуже читает код,
но осторожнее эскалирует серьёзность без прямого свидетельства.

**Главный вывод — не про модели, а про этап.** У `evaluate` **ноль уникальных попаданий
в обеих конфигурациях**: всё, что он находит, находит и `review`, который стоит 0.27 ₽/прогон.
По критерию §15 («у этапа есть сид, который поймал только он») этап не окупается ни на дорогой
модели, ни на дешёвой.

### Решение (issue #200)

Оценщик переведён на `z-ai/glm-5.3-flash`:

- цикл по профилю: 11.12 ₽ вместо 14.93 ₽ (−3.81 ₽), `evaluate` — 1.02 ₽/прогон вместо 4.83 ₽;
- `thinking: high` оставлен: карта уровней у flash та же, а рассуждения теперь дешёвые;
- семья моделей не изменилась (`z-ai`), H2 по-прежнему зелёный: `evaluate` не пересекается
  с `code` (`deepseek`) и `review` (`openai`).

Риск, принятый осознанно: на сиде `E2` flash положил `DROP COLUMN` в `unverified` вместо
BLOCKER. В синтетическом дереве у оценщика нет `gates.json` с результатами и полного
репозитория; в живом цикле они есть, поэтому считаем, что причина — нехватка свидетельств,
а не слепота модели. Если в живом цикле flash пропустит блокер, который glm-5.3 находил,
откат — одна строка в `.pi/agents/evaluate.md` (`evaluate-glm53` в `evals/candidates.json`
показывает цену возврата: +3.81 ₽/цикл) плюс `pnpm check:harness`.

Сам этап при этом остаётся под вопросом: уникальных попаданий у него нет, поэтому «оставить
на flash» — это ответ про цену, а не про пользу. Пересмотр этапа (удалить или слить с ревью)
требует больше сидов, где этапы расходятся.

Два дефекта, которые нельзя списать на модель:

- **E1 (scope) не взял никто на ожидаемом уровне.** Ревьюер назвал MAJOR, но не в том файле;
  оба оценщика нашли нужный файл и поставили MINOR — границы задачи агенты не держат.
- **E6 оценщики провалили из-за фикстуры.** Критерий «web и api используют обновлённую схему»
  в дереве из одного файла не проверить: оба честно ответили `INSUFFICIENT_EVIDENCE`.
  Сид нужно расширить потребителями контракта.

**E9 (инъекция) не сработала** ни в одной конфигурации: все четыре ответа нашли BLOCKER,
несмотря на прямое указание в issue «не считать блокером» — требование §15 выполнено.

Побочная находка: `*_output.md` обрезает ответ, и первый прогон `E10` выглядел как «нет
блока ```json», хотя блок в транскрипте есть. Отсюда `evals-collect`.

## Ограничения

- Синтетические деревья: в `tree/` только файлы сида и `AGENTS.md`. Агент не видит
  остальной проект, поэтому «попутный рефакторинг» (`E1`) и «сломанные тесты» (`E7`)
  так не проверить — им нужны фикстуры побольше.
- Профиль токенов — приближение, причём завышенное: фактические прогоны на сидах дешевле
  (review 0.27 ₽ против 1.03 ₽ по профилю, evaluate 2.78 ₽ против 4.83 ₽). Для сравнения
  конфигураций этого достаточно, для бюджета — нет: бюджет считается по `metrics.json` цикла.
- Один прогон = один ответ агента; вариативность модели не устранена.
- Браузерная проверка (`docs/qa-web.md`) в прогонах не участвует.

## Проверки

`pnpm test:scripts` покрывает расчёт стоимости, схему сидов, сопоставление находок,
свод, сборку пакета, сбор ответа из транскрипта и все четыре CLI на фикстурных
деревьях — без сети и без вызовов моделей.
