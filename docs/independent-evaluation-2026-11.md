# Независимая экспертная оценка проекта hair-lab

**Дата оценки:** 16 ноября 2026  
**Оценщик:** независимый технический эксперт (fullstack + AI-системы + product engineering)  
**Репозиторий:** https://github.com/DNikulshin/hair-lab  
**Статус на момент оценки:** публичный, ~76 коммитов, ~297 файлов, 31 open issue, 0 stars

---

## 1. Краткое резюме

**hair-lab** — это production-oriented monorepo для сайта и PWA одного салона красоты (каталог услуг и мастеров, онлайн-запись со слотами, кабинет клиента, оплата через ЮKassa с холдом, transactional outbox для уведомлений).

Проект демонстрирует **высокий уровень инженерной зрелости** для соло-разработки. Архитектура, процесс и инфраструктура выстроены с явным приоритетом поддерживаемости, надёжности и безопасности персональных данных, а не скорости «фич любой ценой».

**Общая оценка: 8.7 / 10**

Это один из самых сильных примеров соло-проекта с AI-assisted разработкой, которые я видел в 2025–2026 годах. Основная ценность — не в «ещё одном букинг-сайте», а в качестве инженерной системы вокруг него.

---

## 2. Контекст и цели проекта

- **Бизнес-цель:** рабочий инструмент для одного салона (запись, каталог, кабинет, оплата).
- **Техническая цель:** чистая, расширяемая кодовая база с возможностью будущего мобильного клиента (Expo) и минимальным техническим долгом.
- **Организационная модель:** один разработчик + AI-агенты (pi) с жёсткими правилами.

Проект явно не позиционируется как SaaS-платформа для множества салонов. Это правильное ограничение на текущем этапе.

## 3. Архитектура и технический стек

### Сильные стороны

| Аспект                        | Оценка  | Комментарий                                                                                                 |
| ----------------------------- | ------- | ----------------------------------------------------------------------------------------------------------- |
| Монорепо-организация          | Отлично | pnpm workspaces + Turborepo. Чёткое разделение `apps/`, `packages/`, `tooling/`, `scripts/`, `docs/`        |
| API (Fastify 5)               | Отлично | Feature-as-plugin, слои `app → features → services → shared`, единый формат ошибок, Zod через type-provider |
| Контракты                     | Отлично | `packages/contracts` как единственный источник истины. Обратная совместимость зафиксирована правилами       |
| Frontend (Next.js App Router) | Хорошо+ | PWA, Tailwind v4, feature-слои, бренд из env. Визард записи и кабинет выглядят продуманными                 |
| Данные                        | Отлично | Prisma + только миграции, expand/contract, идемпотентность записи, UTC + timezone салона                    |
| Надёжность                    | Хорошо  | Transactional outbox, unique/exclusion constraints на слоты, healthcheck                                    |
| Безопасность ПДн              | Отлично | Маскирование, запрет реальных данных в тестах/логах, проверка владельца до кэша                             |
| Инфраструктура                | Хорошо+ | Docker-образы (api/web/migrations), CI → GHCR, staging/preprod, deploy-скрипты с автооткатом образа         |
| Проверка архитектуры          | Отлично | `pnpm check:arch` — BLOCKER при нарушении границ слоёв                                                      |

### Архитектурные решения, которые заслуживают уважения

1. **Контракты как package** — правильный путь для будущих клиентов (web + потенциальный Expo).
2. **Жёсткие границы слоёв** + автоматическая проверка — редкость даже в командах из 5–10 человек.
3. **ADR-практика** уже с самого начала (0001 Fastify, 0006 независимая оценка и т.д.).
4. **Минимализм deployable-единиц** — новые сервисы только через ADR и при реальной необходимости.
5. **Outbox-паттерн** для уведомлений — показывает понимание реальной надёжности.

### Слабые / рисковые места

- `/health` пока не проверяет БД (есть в бэклоге как B2).
- Нет автоматических бэкапов БД перед миграциями (B1).
- Rate-limiting пока только на auth-эндпоинтах (B3).
- PWA offline-поведение для персонализированных данных осознанно ограничено (правильно), но UX записи в офлайне может потребовать доработки.

## 4. Процесс разработки и AI-оркестрация

Это **самая интересная и сильная часть проекта**.

### Текущий цикл (`/cycle`)

- Супервизор (DeepSeek-v4.1-flash) + субагенты `plan` / `code` / `review`.
- Артефакты в `.pi/artifacts/`.
- Максимум 2 итерации code.
- Жёсткие правила в `AGENTS.md` (границы, ПДн, git-процесс, минимальные правки).

### Направление развития (orchestrator v0.2 + handoff)

Проект переходит от «LLM принимает решения» к **детерминированному ядру**:

- `cycle-state`, `cycle-gates`, `cycle-decide`, `cycle-evidence`, `cycle-pr-body`, `cycle-metrics`
- Независимый агент `evaluate` (слепой к плану и отчётам исполнителя)
- Машинные свидетельства вместо заявлений модели
- Формальный конечный автомат состояний
- `check-harness` для защиты самого оркестратора

Это очень зрелый и правильный вектор. Большинство AI-coding систем остаются на уровне «умный чат с инструментами». Здесь строится **управляемый процесс с проверяемыми доказательствами**.

**Оценка AI-процесса: 9.2 / 10** (с учётом текущего состояния + направления).

Стоимость разработки (по cost-report) крайне низкая благодаря тяжёлому кэшированию и дешёвым моделям (~8 ₽ за несколько дней интенсивной работы). Это важный сигнал: процесс экономически устойчив.

## 5. Качество кода и документации

- Документация (`AGENTS.md`, `docs/`, ADR) — на уровне сильных open-source проектов.
- Единый источник правил для агентов.
- Pre-commit хуки + CI с архитектурными проверками.
- Линейная история (squash), защита `main`, issue-driven процесс с Kanban-метками.

Код (по структуре и правилам) выглядит дисциплинированным. Прямой аудит каждой строки не проводился, но инфраструктура вокруг кода значительно снижает риск «грязных» изменений.

## 7. Риски

### Технические

- Зависимость от текущего набора моделей и провайдера `polza-ai`.
- Сложность самонастройки оркестратора (T7 — критическая точка).
- Потенциальный дрейф документации vs реального поведения скриптов.

### Организационные

- Один разработчик = single point of failure (хотя процесс это частично компенсирует).
- Высокая когнитивная нагрузка на поддержание AI-цикла и правил.

### Продуктовые

- Отсутствие публичного демо и метрик использования.
- Сертификат `*.dnikulshin.ru` истекает ~30 января 2027 — нужно автоматизировать (B5).

## 9. Рекомендации

### Краткосрочные (до первого продакшен-релиза)

1. Закрыть B2 (`/health` с проверкой БД) и B1 (бэкапы).
2. Завершить фазу 1 оркестратора (T0–T9) и провести боевой прогон.
3. Добавить публичный preview / скриншоты / краткое описание в README.
4. Автоматизировать продление сертификата (B5).

### Среднесрочные

1. Полировка UX визарда записи и кабинета (особенно edge-cases).
2. Метрики использования и error-tracking.
3. Rate-limiting на запись и слоты.
4. Рассмотреть лёгкий admin-интерфейс для мастеров/владельца салона.

### Долгосрочные

1. Если появится спрос — мульти-салонность через tenant-изоляцию (не раньше, чем нужно).
2. Мобильный клиент на Expo (контракты уже к этому готовы).
3. Вынос AI-оркестратора в отдельный переиспользуемый слой (если будет ценность).

## 11. Заключение

**hair-lab** — это не просто приложение для салона. Это пример того, как можно строить программный продукт в эпоху AI-агентов: с жёсткими правилами, проверяемыми границами, evidence-based решениями и очень низкой стоимостью итераций.

Сильные стороны проекта системные, а не точечные. Слабые стороны в основном связаны с незавершённостью операционной готовности (бэкапы, health, сертификат) и слабым внешним позиционированием — всё это исправимо без изменения фундамента.

**Рекомендация:** продолжать в выбранном направлении. После закрытия фазы 1 оркестратора и операционных блокеров B1/B2 проект будет готов к реальной эксплуатации и станет сильным кейсом как инженерной культуры, так и эффективного AI-assisted development.
