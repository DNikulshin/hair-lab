# Миграции: expand/contract и откат

Источники истины: `AGENTS.md` («Данные и надёжность»), `docs/deploy.md` («Миграции»),
`apps/api/prisma/schema.prisma` и каталог `apps/api/prisma/migrations`. Здесь — короткая
процедура и разбор конкретной миграции как образец.

## Как делается изменение схемы

```bash
export DATABASE_URL='postgresql://hair_lab:change_me@127.0.0.1:55432/hair_lab?schema=public'
pnpm --filter @hair-lab/api db:migrate:dev --name <snake_case_имя>   # создать и применить
pnpm --filter @hair-lab/api db:migrate:deploy                        # накатить на окружение
```

- Миграции `prisma migrate`, ничего кроме них (`db push`, `migrate reset`, `--force-reset`
  запрещены).
- Применённые миграции не правятся: ошибка исправляется новой миграцией.
- Несовместимое изменение делится на шаги, каждый — своя миграция и свой деплой:
  1. **expand** — новая таблица/колонка, старые читатели продолжают работать;
  2. бэкфилл данных (идемпотентный, батчами);
  3. **contract** — `NOT NULL`/переименование/удаление, когда все читатели обновлены.
- Сгенерированный `migration.sql` проверяется глазами: Prisma не выражает `EXCLUDE`, `CHECK`,
  `btree_gist` — это дописывается в тот же файл руками (образец — `20261112234607_init_db_schema`).

## Откат

Prisma не умеет «откатить вниз» миграцию, поэтому откат схемы — это **новая миграция**,
в которой обратные операции лежат внутри `migration.sql`. Так `DROP` остаётся в миграции
(требование AGENTS.md), а история `_prisma_migrations` не расходится со схемой: применили
миграцию — значит применили и откат следующей.

```bash
# 1. Обратные операции — в новой миграции, не в прежней (применённые не правятся).
pnpm --filter @hair-lab/api db:migrate:dev --name revert_<что_откатываем>

# 2. Применить обычным путём: миграция накатывается как любая другая.
pnpm --filter @hair-lab/api db:migrate:deploy
```

`prisma migrate resolve --rolled-back <имя_миграции>` — **не инструмент отката схемы**.
Он для другого случая: миграция упала посередине, и её нужно пометить неприменённой, чтобы
`migrate deploy` попробовал снова (порядок — `docs/deploy.md` «Если миграция упала»).
Для успешно применённой миграции он не подходит: строка в `_prisma_migrations` станет
«откаченной», объекты останутся в схеме (или наоборот — если убрать их руками, история
и схема разойдутся, а `migrate deploy` таблицы не вернёт).

Правила:

- ручной DDL в БД, включая `DROP`/`TRUNCATE`, запрещён: и в dev, и в проде обратные
  операции идут миграцией (`AGENTS.md`, «Данные и надёжность»); ручные правки прод-БД —
  только крайний случай с разбором в отдельном issue (`docs/deploy.md`);
- откат допустим, пока миграция не попала в прод **или** пока удаляемые объекты не содержат
  данных, которые нужны работающему коду;
- откат нового кода и схемы идёт в обратном порядке: сначала старый образ, потом схема;
- `DROP TABLE`/`DROP TYPE` в откатной миграции — только для объектов, созданных откатываемой
  миграцией (у нас — `BEGIN; … COMMIT;` в файле, как у `20261117193026_add_staff_auth`);
- если миграция упала посередине, порядок восстановления — `docs/deploy.md` («Если миграция
  упала»).

## `#240 add_staff_auth` — только expand, откат безопасен

Миграция `20261117193026_add_staff_auth` добавляет учётные записи сотрудников:

| Объект           | Что создано                                                                                                                                   |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `staff_role`     | enum (`admin`, `manager`)                                                                                                                     |
| `staff`          | `id`, `email` (unique), `password_hash`, `role`, `is_active`, отметки времени                                                                 |
| `staff_sessions` | `id`, `token_hash` (unique), `staff_id` (FK → `staff`, `ON DELETE CASCADE`), `created_at`, `last_used_at`, `expires_at`, индекс по `staff_id` |

Это фаза **expand**: только новые объекты, существующие таблицы и колонки не меняются, старые
версии клиентов и предыдущий образ API продолжают работать. Фаза **contract** не нужна:
скрывать нечего, `NOT NULL`-переходов по существующим данным нет.

Откат (пока сотрудников нет или их данные не нужны) — отдельной миграцией
`revert_add_staff_auth`, порядок — обратный созданию:

```sql
BEGIN;
DROP TABLE IF EXISTS "staff_sessions";
DROP TABLE IF EXISTS "staff";
DROP TYPE IF EXISTS "staff_role";
COMMIT;
```

`DROP` здесь легален именно потому, что он внутри миграции: `prisma migrate deploy` применит
её как шаг истории, и `_prisma_migrations` останется согласованной со схемой. Руками этот SQL
не выполняется. Данных сотрудников на момент отката нет (учётные записи создаются поштучно
CLI `pnpm create:staff`), поэтому потери данных не происходит. Если сотрудники уже заведены,
откат схемы невозможен без потери учётных записей — тогда вместо отката выпускается новая
миграция.
