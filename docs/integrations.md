# Внешние интеграции

Все секреты — только в окружении (`.env` на VPS, GitHub Secrets для CI). В репозиторий,
issues и тесты попадают лишь вымышленные значения. В коде секреты читаются один раз
при старте и валидируются Zod.

## ЮKassa (оплата записи)

Решение: полная оплата записи онлайн. На этапе разработки используется **тестовый магазин**
ЮKassa — он позволяет пройти весь сценарий без реальных списаний.

Планируемые переменные окружения API:

| Переменная            | Назначение                                              |
| --------------------- | ------------------------------------------------------- |
| `YOOKASSA_SHOP_ID`    | идентификатор магазина                                  |
| `YOOKASSA_SECRET_KEY` | секретный ключ (только в `.env`/секретах)               |
| `YOOKASSA_RETURN_URL` | возврат клиента после оплаты                            |
| `PAYMENTS_MODE`       | `test` или `live` — защита от случайных боевых платежей |

Принципы:

- сумма и назначение платежа определяются на сервере, не приходят от клиента;
- вебхук проверяет подлинность и обрабатывается идемпотентно (повтор не меняет состояние);
- запись подтверждается только после успешной оплаты; истёкшая оплата освобождает слот;
- секретный ключ не логируется, тела вебхуков логируются без персональных данных.

## Email

**Решение (ADR 0004, issue #26):** свой ящик `no-reply@<домен>` на домене салона у российского
провайдера, отправка по SMTP. Разбор вариантов и условия пересмотра — `docs/email-providers.md`.

| Вариант                               | Хост                 |
| ------------------------------------- | -------------------- |
| Яндекс 360 для бизнеса (по умолчанию) | `smtp.yandex.ru:465` |
| VK WorkMail                           | `smtp.mail.ru:465`   |

Почему не транзакционный сервис: владелец выбрал свой ящик и отказ от трансграничной передачи
данных. Ограничения приняты осознанно:

- вебхуков о доставке нет — статус определяется по SMTP-ответу (5xx → suppression list,
  4xx/таймаут → ретрай с backoff);
- лимит отправки держим сами: ~30 писем в минуту, ~200 в сутки;
- обязательны SPF, DKIM, DMARC, иначе письма о записи попадут в спам;
- при росте объёма или проблемах с доставляемостью — переход на API-провайдера
  (Unisender/Mailopost) через адаптер `EmailTransport`, без правки бизнес-логики.

Переменные:

| Переменная        | Тип             | Значение                                           |
| ----------------- | --------------- | -------------------------------------------------- |
| `SMTP_HOST`       | GitHub Variable | `smtp.yandex.ru` (по умолчанию) или `smtp.mail.ru` |
| `SMTP_PORT`       | GitHub Variable | `465`                                              |
| `SMTP_SECURE`     | GitHub Variable | `true`                                             |
| `SMTP_USER`       | GitHub Variable | `no-reply@<домен>`                                 |
| `SMTP_PASSWORD`   | GitHub Secret   | пароль приложения из панели провайдера             |
| `SMTP_FROM_EMAIL` | GitHub Variable | `no-reply@<домен>` (по умолчанию = `SMTP_USER`)    |
| `SMTP_FROM_NAME`  | GitHub Variable | «Стриж Lab»                                        |

Адрес отправителя должен совпадать с доменом салона; ответы клиентов — на отдельный ящик
`hello@<домен>` (поле `Reply-To`).

### Очередь писем (outbox)

Письмо никогда не отправляется внутри запроса: событие пишет строку в `outbox_messages`
в одной транзакции с бизнес-записью (transactional outbox), а отправляет фоновый диспетчер
в процессе API (интервал ~10 с, пачка до 10 писем). Сбой SMTP не ломает создание записи.

- Строка outbox создаётся **всегда, когда клиент оставил email**; без email письма нет.
- Повтор запроса по `idempotencyKey` (200) и проигранная гонка за слот (409) не оставляют
  лишних строк: запись и outbox коммитятся вместе или не коммитятся вовсе.
- Статусы: `pending` → `sent` | `failed` | `suppressed`.
  - `5xx` на этапе `RCPT TO` (`550`–`554`, адрес получателя отклонён постоянно) → `suppressed`,
    повторов нет;
  - `5xx` на других этапах (`MAIL FROM`, `DATA`, `AUTH` — отказ отправителю, политика содержимого,
    неверные учётные данные), остальные `4xx`, таймаут, сетевые ошибки и ошибки без этапа →
    повтор с паузой 1, 5, 15, 60 и 240 минут;
  - после исчерпания повторов → `failed`;
  - письмо о событии, которое уже началось, не отправляется → `failed('expired')`.
- Лимиты отправки: ~30 писем в минуту и ~200 в сутки по фактическому `sent_at` (время после
  успешного `send`, а не начала тика); бюджет пересчитывается перед каждым письмом пачки.
- Доставка at-least-once: падение процесса между отправкой и записью статуса даёт редкий дубль.

**Пустой `SMTP_HOST` (по умолчанию в `.env.example`) — модуль почты выключен.** API работает
штатно: записи создаются, строки outbox копятся со статусом `pending`, письма не уходят.
Когда ящик настроен и `SMTP_HOST` заполнен, диспетчер доотправляет **только будущие записи**;
события, которые уже начались, остаются `pending` до первого тика и получают
`failed('expired')`. Ошибки прошлых периодов поэтому не «догоняются» — это осознанно.

Персональные данные: email, имя клиента и тело письма хранятся только в БД; в логах —
идентификатор записи/сообщения, тип письма, код SMTP-ответа и этап отказа (`MAIL FROM`,
`RCPT TO`, `DATA`). `last_error` в лог не пишется.

## Аутентификация (issue #6)

| Переменная    | Тип             | Значение                                                  |
| ------------- | --------------- | --------------------------------------------------------- |
| `AUTH_SECRET` | GitHub Secret   | случайная строка ≥ 32 символов: `openssl rand -base64 48` |
| `APP_URL`     | GitHub Variable | `https://<домен>` — база для ссылок входа и подтверждений |

Валидация при старте: обязательные переменные проверяются всегда, интеграционные —
только когда интеграция включена (`PAYMENTS_MODE`, заполненный `SMTP_HOST`). Пока значения
пустые, API работает без соответствующих модулей.

## nginx на хосте

Единственная точка входа. Контейнеры опубликованы только на loopback:

- `127.0.0.1:3000` — web;
- `127.0.0.1:3001` — api, снаружи доступен как `/api/*` (префикс отрезается).

Конфиг: `deploy/nginx/hair-lab.conf.example` (TLS, заголовки безопасности, gzip, кэш статики).
Сертификаты — Let's Encrypt (certbot) или уже имеющиеся.

Проверка после настройки: `https://<домен>/` открывается, `https://<домен>/api/health` отдаёт
`{"status":"ok",...}`, а `curl http://127.0.0.1:3001/health` снаружи недоступен.
