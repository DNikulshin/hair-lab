# 0005. Оплата записи через ЮKassa: режимы, холд, свипер, вебхук

- **Статус:** принято
- **Дата:** 2026-11-14
- **Контекст:** запись должна оплачиваться онлайн (issue #8). Провайдер выбран в
  [ADR 0004](./0004-payments-email-nginx.md): ЮKassa, тестовый магазин на этапе разработки.
  Здесь зафиксированы детали, которые определяют поведение API и данных: когда оплата включена,
  сколько слот держится за неоплаченной записью, как проверяется подлинность уведомления,
  что происходит с деньгами, пришедшими после истечения холда.

## Решение

**Режимы.** Оплата включается переменной `PAYMENTS_MODE`:

- `off` (по умолчанию) — оплаты нет: запись создаётся `pending`, письмо-подтверждение уходит
  сразу, поля `payment` в ответе нет. Поведение API не меняется ни на байт, установленные
  PWA-клиенты ничего не замечают;
- `test` — тестовый магазин ЮKassa: весь сценарий проходит без реальных списаний;
- `live` — реальные деньги.

Ключи магазина (`YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`) обязательны только при `test|live`:
пустой `.env.example` остаётся валидным, API запускается без платежей. Утечка режима в `live`
по умолчанию исключена намеренно: включение боевых платежей — осознанное действие.

**Холд 15 минут.** Запись с обязательной оплатой создаётся в статусе `pending` с
`appointments.payment_deadline_at = now + 15 минут` плюс строка `payments(pending)` — в одной
транзакции. Нового значения в enum `appointment_status` нет: неизвестный статус сломал бы разбор
ответа `bookingStatusSchema` у уже установленных клиентов, а `pending` + дедлайн + платёж
выражают холд полностью. Письмо-подтверждение в этой транзакции не пишется: клиент получает
его только после оплаты (в режиме `off` — как раньше, сразу).

15 минут — компромисс между «успеть ввести карту» (реальный сценарий оплаты: 3–7 минут)
и «не держать слот» (за это время его может занять другой клиент). Значение живёт в коде
(`PAYMENT_HOLD_MINUTES`), а не в окружении: это продуктовое правило, а не настройка среды.

**Платёж в шлюзе — после коммита.** Запись и строка платежа фиксируются без сетевых вызовов,
затем создаётся платёж в ЮKassa с `Idempotence-Key: payment-<appointmentId>`, а его id и ссылка
на оплату сохраняются в `payments`. Ссылка и дедлайн холда возвращаются клиенту в аддитивном
поле `booking.payment`. Сбой шлюза не оставляет занятый слот: запись отменяется
(`cancelled`, причина `payment_creation_failed`), платёж становится `canceled`, клиент получает 502. Отдельного кода ошибки в контракт не добавляем — используется существующий
`internal_error`: старые клиенты разбирают тело ошибки Zod-схемой и упали бы на новом коде.

**Свипер истёкших холдов — в процессе API.** Тик раз в 30 секунд (`PAYMENT_SWEEP_INTERVAL_MS`)
отменяет записи с истёкшим `payment_deadline_at` (`cancelled`, причина `payment_expired`) и
переводит их платежи в `canceled`. Отдельный `worker` не нужен: API работает в одном экземпляре
(AGENTS.md, «Допущения о развертывании»), а один таймер не стоит ещё одного deployable — это
прямо противоречило бы критериям ADR-процесса. Условия отбора стоят в `WHERE` самого `UPDATE`,
поэтому между тиком и оплатой нет окна: подтверждённая запись в выборку не попадает.

**Аутентификация уведомления.** Подписи ЮKassa не присылает, поэтому:

1. IP отправителя (`request.ip` с учётом `trustProxy`) сверяется с allowlist провайдера
   (`isYookassaIp`); адрес вне списка → 403, состояние не меняется, в лог — только id платежа;
2. состояние платежа перезапрашивается у провайдера своими ключами (`GET /v3/payments/{id}`),
   телу уведомления не доверяем: событие в нём — лишь повод сходить за фактом;
3. сумма из ответа сверяется с `payments.amount_kopecks`: расхождение → `failed`-лог, ответ 200,
   состояние не меняется (деньги приняты не по нашему расчёту — разбирается вручную).

**Код ответа — просьба к провайдеру, а не «всегда 200».** 200 отдаётся только когда уведомление
заведомо ничего не меняет: неизвестный/чужой платёж, платёж ещё не завершён у провайдера,
расхождение суммы при сверке — повторять такое незачем. Если перезапрос состояния упал (сеть,
5xx провайдера), ответ — 5xx (`internal_error`): ЮKassa повторит доставку (до 24 часов).
200 в этом случае значил бы «обработано», а оплаченная запись осталась бы `pending` и была бы
отменена свипером без возврата денег.

Rate limit на уведомления не ставится: они приходят пачками с адресов провайдера, лимит
превратил бы всплеск в отказы и повторные доставки 24 часа.

**Идемпотентность.** У каждого перехода статуса условия стоят в `WHERE` самого `UPDATE`
(статус платежа, статус записи), письмо-подтверждение пишется только если его ещё нет.
Повтор уведомления — no-op с текущим состоянием; повтор `POST /v3/refunds` с ключом
`refund-<paymentId>` (его используют и обработчик уведомления, и свипер) деньги дважды не
возвращает; повтор `POST /bookings` по `idempotencyKey` (200) не создаёт второй платёж и не
обращается к шлюзу; проигранная гонка за слот (409) платежа не создаёт.

**Автовозврат при оплате после истечения холда.** Если деньги пришли по записи, которую уже
нельзя подтвердить (холд истёк, запись отменена), платёж фиксируется как полученный, деньги
возвращаются через `POST /v3/refunds` (`Idempotence-Key: refund-<paymentId>`), платёж становится
`refunded` — но только когда провайдер ответил `succeeded` (ниже). Факт получения денег не теряется
даже при сбое возврата: платёж остаётся `succeeded` и виден в БД.

**Возврат завершён только при `succeeded`.** Ответ `POST /v3/refunds` со статусом `pending`
(деньги ещё в пути), `canceled` (провайдер отказал) или нераспознанным не снимает обязанность
вернуть деньги: в `payments.refund_required` остаётся/ставится флаг, платёж в `refunded`
не переходит. Флаг живёт в БД (не в памяти процесса), поэтому переживает сбой шлюза и перезапуск,
а свипер добивает возврат в своём тике тем же ключом `refund-<paymentId>` — повтор деньги дважды
не вернёт. `canceled` означает отказ провайдера: он виден в логе уровня error и требует ручной
проверки, но цикл повторов при этом не останавливается.

**Новых зависимостей нет.** Клиент ЮKassa — тонкий адаптер на `fetch` за интерфейсом
`PaymentGateway` (создать платёж, прочитать платёж, вернуть деньги). В тестах шлюз подменяется
поддельным объектом через опции `buildServer`, а не мутацией `process.env`: режим оплаты —
зависимость композиционного корня, как `emailEnabled` у почты.

**Статус оплаты для клиента.** `GET /bookings/:id/payment` отдаёт только
`{ status, appointmentStatus }` по UUID записи. Персональных данных в ответе нет, поэтому
авторизация для страницы статуса (PR2) не требуется: идентификатор — единственная «защита»,
а раскрывать по нему нечего.

## Последствия

- Положительные:
  - `PAYMENTS_MODE=off` по умолчанию — релиз не меняет поведение уже установленных клиентов;
  - деньги и назначение платежа считаются только на сервере, ПДн клиента в ЮKassa не уходят
    (`metadata = { appointmentId }`, описание — только название услуги);
  - сбой провайдера не ломает запись: компенсация отменяет холд, слот снова свободен;
  - контракты изменены аддитивно (`booking.payment?`), новых кодов ошибок нет;
  - нет новых зависимостей и нового deployable — интеграция проверяется поддельным шлюзом.
- Отрицательные / цена:
  - между истечением холда и тиком свипера слот занят до 30 секунд (осознанно, один инстанс);
  - уведомление, пришедшее в окно между созданием платежа в шлюзе и сохранением его id,
    не найдёт нашу строку и будет проигнорировано — редкий сценарий, разбор в follow-ups;
  - возврат зависит от доступности API ЮKassa: при сбое платёж остаётся `succeeded` с
    `refund_required = true`, возврат повторяет свипер — деньги не теряются, но клиент ждёт;
    ручная проверка нужна только при отказе провайдера (`canceled`);
  - холд — вектор для искусственного занятия слотов; анти-абьюз и rate limiting на
    `POST /bookings` — отдельная задача (follow-up);
  - повторное создание платежа при сбое шлюза не делается: клиент создаёт запись заново.
- Что становится запрещено:
  - принимать сумму, назначение платежа или статус оплаты от клиента;
  - доверять телу уведомления без перезапроса состояния и сверки суммы;
  - добавлять новое значение в enum `appointment_status` (ломает разбор у старых клиентов);
  - писать персональные данные клиента в запросы к ЮKassa, в логи уведомлений и в тексты ошибок;
  - запускать свипер вторым процессом или отдельным worker'ом без нового ADR.

## Условия пересмотра

- Появление второго экземпляра API или требование «слот свободен ровно в дедлайн» — свипер
  выносится в отдельный процесс/крон и получает блокировку (`pg_advisory_lock`);
- переход на чеки 54-ФЗ (`receipt` в платеже) — отдельный ADR: меняются данные платежа и налоги;
- появление подписи/IPv6-изменений у провайдера — пересмотр `isYookassaIp` и способа
  аутентификации уведомлений (например, общий секрет в пути);
- если повторов возврата в тике свипера станет недостаточно (частые `canceled`, долгая
  недоступность ЮKassa) — очередь повторных возвратов с ручным разбором (worker).

## Рассмотренные альтернативы

| Вариант                                                          | Плюсы                             | Минусы                                                                         |
| ---------------------------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------ |
| Новый статус записи `awaiting_payment`                           | явное состояние                   | ломает разбор `bookingStatusSchema` у установленных PWA-клиентов               |
| Холд на стороне ЮKassa (`capture: false` + двухстадийная оплата) | деньги резервирует провайдер      | подтверждение и отмена — отдельные вызовы; срок холда не наш; больше состояний |
| Свипер в отдельном worker/cron                                   | не зависит от числа инстансов API | новый deployable ради одного таймера; противоречит критериям ADR-процесса      |
| Официальный SDK ЮKassa                                           | готовые запросы и ретраи          | новая зависимость ради трёх вызовов; SDK тянет транзитивные пакеты             |
| TTL-поле `expires_at` платежа как дедлайн слота                  | не нужно своё поле                | провайдер не гарантирует связь с нашим слотом; дедлайн нужен и при сбое шлюза  |
| Новый код ошибки `payment_failed` (502)                          | точнее для клиента                | старые клиенты парсят тело Zod-схемой и упадут на неизвестном коде             |
