# hair-lab (сайт и PWA салона красоты) — инструкции для AI-агентов

> Единый источник правил для агентов (pi, Claude Code и др.). `CLAUDE.md` тонкий и ссылается сюда.
> Окружение, деплой и принятые решения — в `docs/` (здесь не дублировать).

## Проект

Сайт и PWA одного салона красоты: каталог услуг, мастера, онлайн-запись, кабинет клиента.
Разрабатывает один человек. Стабильность и отказоустойчивость важнее скорости новых фич.
Возможен будущий клиент на Expo, поэтому контракты API должны быть клиент-нейтральными.

## Стек и структура

- pnpm workspaces + Turborepo; версия Node — из `.nvmrc` / `engines`
- `apps/web` — Next.js (PWA); `apps/api` — Fastify; PostgreSQL + Prisma
- `packages/contracts` — Zod-схемы и типы API, источник истины для всех клиентов
- `tooling/*` — eslint, prettier, tsconfig
- Позже, по необходимости: `apps/worker` (уведомления, очередь), `apps/mobile` (Expo)
- Стартовый состав минимальный. Новый deployable (сервис) — только через ADR (`docs/adr/`)
  и если выполнено большинство критериев: самостоятельная ответственность, собственные данные,
  отдельный lifecycle или скейлинг, чёткий контракт. Монорепо — способ организации кода,
  а не повод дробить систему на сервисы.
- Репозиторий: https://github.com/DNikulshin/hair-lab; scope пакетов `@hair-lab/*`.
- Выбор Fastify для API принят (первый ADR: `docs/adr/0001-fastify-api.md`).

## Команды

Если скрипта нет в `package.json` — сообщи об этом, команду не выдумывай.

| Что                                                    | Команда                                                   |
| ------------------------------------------------------ | --------------------------------------------------------- |
| Установка                                              | `pnpm install`                                            |
| Сборка контрактов (обязательно перед типами и тестами) | `pnpm --filter @hair-lab/contracts build`                 |
| Типы                                                   | `pnpm typecheck`                                          |
| Линтер                                                 | `pnpm lint`                                               |
| Границы слоёв и пакетов                                | `pnpm check:arch`                                         |
| Unit-тесты                                             | `pnpm test`                                               |
| Интеграционные тесты (нужны Postgres и окружение)      | `pnpm test:int`                                           |
| Новая миграция (dev)                                   | `pnpm --filter @hair-lab/api db:migrate:dev --name <имя>` |
| Применить миграции                                     | `pnpm --filter @hair-lab/api db:migrate:deploy`           |
| Запуск в dev                                           | `pnpm dev`                                                |

Порядок проверки после правок: `contracts build` → `typecheck` → `lint` + `check:arch` → затронутые тесты.
Проверку, которую нельзя выполнить (нет БД, окружения), помечай «не проверено» и называй причину.
Не заявляй «проверено» без фактического запуска.

## Архитектура (ED small)

Внутри `apps/api` и `apps/web` слои: `app → features → services → shared`.

- `app` — запуск, композиция, роутинг. Логику фич в `app` не держим (в Next.js `page.tsx` тонкий).
- `features` — крупные смысловые куски функциональности, где живёт большая часть кода.
  Не дробить мелко: 3–4 фичи на старте нормально.
- `services` — переиспользуемые бизнес-модули; создавать только когда одна и та же самостоятельная
  логика нужна нескольким фичам. Пустой слой «на будущее» не создавать.
- `shared` — последнее место для кода: глобальные типы, инфраструктура, конфиг.
- Запрещено: `features → app`, `services → app/features`, `shared → app/features/services`.
- Импорт feature → feature допустим, но редкий; если связей много — пересмотреть границы фич.
- Эволюция модуля: один файл → плоская папка → группы (`ui/model/lib/api/domain`) → подмодули → `compose`.
  Усложнять только когда текущая форма реально мешает. Папку с одним файлом не создавать.
- Файл до ~400 строк с одной ответственностью допустим; не дробить ради дробления.
- Публичный API модуля: `index.ts` (в `apps/api`); в Next.js — приватные файлы с префиксом `_`, публичные без.
- Fastify: `app` собирает сервер и регистрирует плагины; feature оформляется как инкапсулированный
  Fastify-плагин (routes + service + схемы). Валидацию строим на Zod-схемах из `contracts`
  (рекомендуется `fastify-type-provider-zod`). Общие плагины (БД, auth, логгер) живут в `shared`
  и не импортируют features.
- Группа (`ui/`, `model/`) — это навигация и не требует public API; модуль — абстракция и требует.
- Правила границ проверяются `pnpm check:arch`; нарушение считается BLOCKER.

## Контракты (`packages/contracts`)

- Zod-схемы — источник истины; типы выводятся через `z.infer`, параллельно руками не пишутся.
- Только чистый TypeScript и Zod: без `node:`-модулей, DOM, React. Бизнес-логики нет.
- Изменения только обратно совместимые (новые опциональные поля, депрекация вместо удаления):
  старые версии клиентов живут неделями (кэш PWA, позже мобильное приложение).
- Порядок изменения: `contracts` → `api` → клиенты. Публичный API пакета — через `index.ts`.
- Все приложения ставятся через pnpm и подключают `contracts` как workspace-зависимость.
  Единая версия React / React Native во всём воркспейсе. Если Expo упрётся в изолированные
  зависимости — `nodeLinker: hoisted` в `pnpm-workspace.yaml` с записью причины в `docs/`.

## Данные и надёжность

- Схема БД меняется только версионированными миграциями (`prisma migrate`), по схеме expand/contract.
  Применённые миграции не править — создавать новую.
- Запрещено: `prisma db push`, `prisma migrate reset`, `--force-reset`, `--accept-data-loss`,
  `DROP`/`TRUNCATE` вне миграции, любые ручные правки продовой БД.
- Запись на услугу: уникальность слота обеспечивается на уровне БД (unique / exclusion constraint),
  создание записи идемпотентно (idempotency key). Время хранится в UTC, часовой пояс салона — в конфиге;
  учитывать переход на летнее/зимнее время.
- Уведомления выполняются вне транзакции записи (outbox + очередь, ретраи, DLQ).
  Сбой провайдера сообщений не должен ломать создание записи.
- Публичные страницы — статика/ISR. Service worker PWA не кэширует ответы API с персональными данными.
- Ориентиры надёжности (предложены, подтвердить): RPO ≤ 15 мин, RTO ≤ 1 ч.

## Персональные данные и безопасность

- Данные клиентов (имя, телефон, email, история визитов) — персональные. Не печатать их в ответах,
  логах, тестах, сидах и фикстурах: в тестах только вымышленные данные. Телефоны в логах маскируются.
- Секреты: `.env*` (кроме `.env.example`) не читать и не печатать, в код и документы не записывать.
- Клиент видит только свои записи. Проверка владельца выполняется до чтения кэша и тяжёлых данных.
- Весь внешний ввод валидируется Zod на границе. Запросы к БД параметризованные.

## Git, issues, Kanban

- Работа идёт по issues: каждая задача — issue с метками `type:*`, `area:*`, `prio:*`.
  Статусы (колонки доски) — метки `status:todo|in-progress|review|blocked`.
- Ветки: `feat/*`, `fix/*`, `chore/*`, `data/*`, `design/*` от `main`, имя содержит номер issue.
- merge в `main` делает только владелец после проверки. Прямой push в `main`, force-push
  и удаление `main` запрещены. Merge — squash, история линейная.
- Настройка меток, вех и бэклога — `./scripts/gh-setup.sh`, правила ветки — с `--protect`.
- Подробности и Definition of Done: `docs/workflow.md`.

## Границы действий агента

- Коммитить и пушить можно только в рабочую ветку по текущей задаче (см. «Git, issues, Kanban»).
  PR открывает агент, проверяет и мержит — владелец. Коммиты и push в `main` — запрещены,
  кроме первичного bootstrap пустого репозитория, явно согласованного с владельцем.
- Правки минимальные, в рамках задачи; без попутного рефакторинга и переименований.
- Новая зависимость — только с обоснованием в ответе.
- Не трогать: `node_modules/`, `dist/`, `.next/`, `.turbo/`, сгенерированный Prisma client,
  `pnpm-lock.yaml` (кроме осознанного изменения зависимостей).
- Не выдумывай команды, пути, файлы и API. Если не уверен — прочитай код или спроси.
- Неоднозначная задача: перечисли 2–3 варианта с плюсами и минусами вместо догадок.
- Всё, что обнаружено вне скоупа задачи, фиксируется как follow-up, а не правится попутно.

## Цикл разработки

`/cycle <задача>` запускает `plan → code → review`. Артефакты — в
`.pi/artifacts/<YYYY-MM-DD>-<номер>-<slug>/` (каталог в `.gitignore`):
`plan.md` → `code-report.md` → `review.md` → `followups.md`.

Субагенты проекта лежат в `.pi/agents/` (`plan`, `code`, `review`) — они перекрывают
одноимённых глобальных, поэтому модели и промпты правятся под проект здесь.
Команда `/cycle` — `.pi/prompts/cycle.md`, настройки моделей и лимитов — `.pi/settings.json`.
По умолчанию (общая политика в `~/.pi/agent/`): главная модель и `code` — GPT-6 Luna Pro (thinking medium),
план — GLM-5.3 (thinking high), ревью — GLM-5.3 (thinking high). Ревьюер намеренно из другого
семейства, чем автор кода. План и ревью делят модель — это осознанный компромисс: третье семейство
(например `anthropic/claude-haiku-5.5`) добавляет независимости, но качество его ревью не проверено.

- Цикл нужен для задач про данные, контракты, авторизацию, платежи, миграции.
  Мелкие правки делаем напрямую.
- Новую итерацию запускают только BLOCKER/MAJOR внутри скоупа плана, подтверждённые сценарием воспроизведения.
  Замечания вне скоупа или существовавшие до диффа идут в `followups.md` и итерацию не запускают.
- Максимум 2 итерации. Третья — только с явного разрешения пользователя и с заново зафиксированным скоупом.

## Допущения о развертывании

Один экземпляр `api` (и `worker` позже). Многоинстансовость не требование, пока она не записана в ADR;
замечания про неё ревьюер оформляет не выше FOLLOW-UP.

## Актуальный контекст через local-rag

В начале каждой новой сессии в проекте, после чтения этих инструкций:

1. Определи корень репозитория (`git rev-parse --show-toplevel`). Если доступен MCP `local-rag`, запусти `local-rag_sync_start` только для `<корень>/docs` и дождись конечного состояния через `local-rag_sync_status`. Это обновит изменённые документы и удалит из индекса документы, которых больше нет.
2. После получения задачи ищи релевантные решения/архитектуру через `local-rag_query_documents` с `scope=<корень>` и конкретным запросом по задаче. Не ищи по всей базе без scope.
3. Используй результаты как навигацию к источникам, а не замену им: `AGENTS.md`, текущий код и актуальные файлы `docs/` — источники истины; при важных решениях открой соответствующий файл напрямую.
4. Если MCP/local-rag недоступен или синхронизация завершилась ошибкой, прочитай соответствующие файлы `docs/` напрямую и сообщи, что использован fallback.

Индексируй/синхронизируй только `docs/`, не весь репозиторий и не общий `/home/dev/projects/`: база RAG общая для нескольких проектов. Не отправляй в RAG `.env*`, пользовательские данные, `node_modules`, generated-файлы и `.pi/artifacts/`.
